# 自动周计划与每日完成度 — Gate 2 已确认设计

## Context
依赖现有本地PlanningState、周安排、目标/体重和手动执行；之前两个change均未Gate3，不改其验收状态。
已确认范围为自动周草案＋自动运动记录完成度；手机测试按用户要求延期。
当前HealthKitReader只保留workout原始类型，没有duration/暂停活跃时段；ActivityReport.workouts只有负荷摘要，不能把心率覆盖分钟当运动分钟。
关联specs/001-product.md P-013–P-016、003数据事务、005去重与负荷；本轮批准后同步扩展原权威规格。

## Decisions

### 1. 输入与规则来源
采集经验（刚开始/规律运动）、偏好活动、可用星期、单次时长上限、可选自报典型周运动分钟。
首版自动安排支持步行、骑行、游泳、跑步四类，均为用户选择，不自动推荐陌生类型；其它活动仍可用已有手动模式。
体验参考Apple Fitness+偏好/日程规划、Fitbod的目标/经验/时长输入。竞品算法未公开，不声称数值等同。
WHO一般活动量信息只作背景，不把其成人公共健康参考强制套到个人，更不作为“减重X公斤需要Y分钟”的公式。
新规则为experimental-week-plan-v1，全部数字为本产品可测试的初始安排策略，不是医学验证或处方。

### 2. 首周分钟生成（需Gate2确认的产品参数）
用户需先选可用星期与时间上限（每次5–120分钟），不预填健康值。
N为配置所选星期数（1–7），C=本周实际可安排日期数×floor(每次上限/5)×5；先对单日容量取整，再累计，确保5分钟分块总量可分配。首周剩余日期或截止日期只减少容量，不改变默认周基础。
B：若填写典型周分钟则取其值（至少5分钟）；否则刚开始取10×N，规律运动取20×N。它们是“初始草案默认”，明确不是历史事实；缺健康记录不被当成0。
周草案总量 W=min(C, max(5, floor(min(B,150)/5)×5))。150只是首版生成器上限，不表示医学安全额度或足够减重。
按周一至周日所选日期，轮流分配5分钟块，直到W分完；日上限不超过用户设定。不足每个所选日5分钟时，其余为未安排，解释总量限制；不靠缩短期限突破约束。
活动类型按用户偏好顺序轮转；首版不生成HR区间、速度、配重、组数或高强度训练。
示例：刚开始、周一/三/五、单次上限30分钟且不填周基础 → 周总30分钟、每天10分钟。规律运动同条件 → 周总60分钟、每天20分钟。
计划有逐日日期/类型/目标秒数/版本/来源/解释，支持预览、逐日改动和确认；确认前不覆盖手动计划。旧手动模式始终可用。
首周从用户确认的下一分析日开始；已过去日期不补安排。目标开始/截止日作为日历范围，超出截止不继续宣称减重计划进行中，但可保留普通活动安排。
体重差、截止剩余天数不进入W计算；到期展示目标回顾/续期入口，不堆积“欠下的运动量”。

### 3. 周调整与恢复
周一至周日按固定分析时区；仅对已完整结束周给下一周草案，不在当天反复改目标。
用户反馈轻松/合适/吃力。完整周所有计划日都有明确完成（自动达到或手动确认）或休息确认，且完成日数/计划日数至少80%、反馈轻松 → 可提出总量加5分钟（仍受时间容量和150上限约束）；反馈吃力 → 可提出总量减5分钟（有安排最低5），其它情况保持。
缺记录或未反馈时不推断未运动或疲劳，不提出加量；休息不视为完成，不补课。
任何调整都要用户点采纳；未采纳保留原计划。只生效到未来未处理日期，历史目标/修改理由保留。
沿用当前低准备度可选休息/预设轻量提示；不能自动替换目标后把进度凑成100%。采纳轻量调整保留原目标和调整目标，进度标明采用哪个版本。

### 4. workout采集与兼容
复用已授权workout读取，不新增数量类型或写权限。HealthRecord扩展可选workoutDurationSeconds、activeIntervals和解析状态。
Apple适配层读取HKWorkout.duration及workoutEvents的暂停/恢复信息，核心不引用Apple API。
仅已结束且end≤asOf的记录参与；duration有限且0≤duration≤elapsed。无暂停且duration与elapsed相差≤1秒时，可用整段活跃区间。
有暂停时按事件恢复活跃半开区间，必须边界有效、无嵌套/逆序，且活跃并集时长与duration差≤1秒；跨午夜从这些区间准确切分。无法还原则只显示来源/记录时长供确认，标“时段不足，未自动计入”，不按比例猜测跨日或暂停。
旧缓存缺字段不填end-start；下一次显式完整健康重建才补字段，日常增量不谎称已补全。迁移仍可浏览历史负荷，进度缺数据时提示重建。
workoutType仅支持上述四类的明确映射，其他或多运动混合记录不自动猜测，提示可手动确认。

### 5. 去重匹配与达标
先按005现有同类型候选连通分量和来源优先级去重，不修改负荷公式。用于进度的所有匹配活跃区间再求并集。
按分析日[start,end)裁剪；只匹配当天已采纳计划的活动类型。一天首版一个计划项，避免一个workout多项目重复归属；非匹配活动另列已记录运动，不计该项但可手动替换计划类型。
自动实际秒数=裁剪后区间并集秒数；目标秒数来自已确认计划快照。
完成比例=min(1,实际秒数/目标秒数)，阈值按未取整秒数≥目标秒数，不按显示取整提前达标。显示实际分钟向下取整，并保留秒级解释。
无匹配记录为unknown（“尚无可匹配记录”），有部分时段显示已记录X/目标Y和“记录尚不足目标”，不宣称全天未运动；日期已过去也不自动认定失败。
手动确认完成、休息及自动记录分开显示；手动完成不生成虚构实际分钟，不把手动目标分钟与自动秒数相加。
自动完成状态为由记录派生的结果，不覆写用户手动动作；记录删除/修订后重新计算，可由完成回退并显示变更原因。重复刷新幂等。
每项显示采样日期、来源、生成/刷新时间、计划版本及“运动计划完成度，不是每日减脂结果”。

### 6. 持久化与页面
PlanningState增加可选自动配置、采纳周版本和调整记录，旧字段/旧手动计划不变；新字段采用decodeIfPresent默认，不破坏上一轮planning缓存。
HealthReport新增可选运动完成度字段，或等价独立投影保留在仓库；实际证据保持当前revision、时间窗口和配置版本一致。
所有保存继续actor+expectedRevision+原子提交；清除stop=false保留手动/计划，stop=true删除全部并防止晚到回写。演示生成合成workout时段，不读取或写入真实计划。
不向Watch/Widget发送体重或计划证据；既有快照协议不变。
今天显示当天目标/已记录/状态；活动页提供生成向导、周预览、采纳、逐日修改和自动/手动来源；趋势显示每周执行及体重目标分开，体重期限不暗示运动等于减脂。
每日目标和健康匹配条件改动需预览确认，状态不足原因要具体。大字体/读屏沿用现有规则。

## Architecture
Apple HealthKitReader → Codable HealthRecord可选workout元信息 → 既有归一化/去重 → WorkoutCompletion纯投影。
AutomaticWeekPlanner(配置、固定日历、已确认反馈) → WeeklyPlanDraft → 用户采纳 → PlanningState版本事务。
DashboardModel继续单实例驱动五Tab；视图不读HealthKit；默认规则/模型版本与解释输出同存。

## Risks / Trade-offs
| 风险 | 缓解 |
| --- | --- |
| 冷启动默认被当运动处方 | 明确初始草案，预览后采纳，参数可改，体重/日期不驱动加量 |
| 类型/暂停/跨日/重复误计 | 类型白名单、活跃区间有效性、并集和半开切日；不支持回退待确认 |
| 旧缓存新字段缺失 | 可选解码、不补elapsed，支持显式重建补数据 |
| 自动完成和人工冲突 | 单独来源状态，不叠加分钟，不抹掉休息/手动确认 |
| 未来配置覆盖历史 | 采纳版本和生效日期冻结，自动证据可修订但目标不静默变化 |
| 调整追赶减重期限 | 日期只控制周期，不进分钟/能量公式；不保证达标 |
