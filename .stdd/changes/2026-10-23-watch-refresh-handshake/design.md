# Watch 刷新回执与首次同步 - 技术设计

## Context

Watch 已安装并被系统 Watch App 识别。用户报告前台请求后仍无快照。当前 sendMessage 无 replyHandler；界面在发送前即显示“已请求”，手机回调仅调用 refresh，失败与无快照不会回传。该事实证明诊断缺口，不足以断定未送达根因。

## Decisions

### 1. 请求与接收分层确认

**方案**：请求带标识、协议版本；手机回复明确处理结果，Watch 仅在真实快照通过校验且落盘后提示收到。手机存在快照时先交付可用快照，再尝试读取更新；旧快照仍按原时效规则显示。

**为什么**：不让 HealthKit 刷新耗时或失败阻塞已存在快照，同时避免把请求回执误当成新数据。

**备选方案及排除原因**：
- 只重发 applicationContext：缺少请求处理证据，不能解决无限等待。
- 强制手表独立读取健康：超出范围，也改变既有架构。

### 2. 兼容与有界等待

保留旧 refresh 消息处理与 applicationContext 通道；新版交互消息回复可带同一最小快照，并统一经过现有接收校验。等待回执设置15秒超时，不自动循环请求；迟到结果通过请求标识隔离，较旧 revision 仍被原接收器拒绝。激活失败、不可达、无快照、需要手机连接健康、处理失败分别展示。并发点击合并，清除标记、生产者确认、演示隔离不绕过。

### 3. 真机交付边界

先用合成快照和可控传输/时钟构造失败测试，再真机验证。当前手机是旧包且 Personal Team 不支持 CloudKit；若需更新手机，应另行确认本地测试构建方案，不能静默移除云实现、清数据或覆盖现有可用包。

## Architecture

Watch 点击 → 刷新状态模型 → WatchBridge 发送 → iPhone 回执/现有快照 → DashboardModel 刷新 → publish → WatchBridge 统一接收与原子保存 → UI/组件。Core 仅含纯状态与协议模型，WatchConnectivity 保留在适配层。

## Risks / Trade-offs

| 风险 | 缓解措施 |
|------|----------|
| 旧手机不回复新回执 | 超时明确提示，不声称离线；旧 context 仍能接收 |
| 手机无缓存或刷新失败 | 返回不含健康值的原因，保留上次快照 |
| 清除与迟到快照竞争 | 保留 revision/producer 校验、清除语义与请求隔离 |
| 现有真机缺乏无值诊断 | 用户双端状态与合成集成测试分别记录，不以构建代替同步验收 |
