# 综合周报 - 技术设计（Gate 2待确认）

## Context

用户已确认优先设计综合周报：今天一张摘要卡、趋势二级详情、不增加一级Tab；缺失不补值、不预测减重日期，计划调整需用户确认。Gate 1证据为上一轮范围说明后用户回复“可以”；不是实现授权。保持普通交互模式，Gate 2批准后方可Build。

现有资产：HealthReport.history包含35个分析日的睡眠总分钟与准备度；PlanningState包含手动/自动计划历史、执行标记、体重和目标；WorkoutCompletion已有类型匹配、活跃区间去重与精确秒数判断。现有近7日健康回顾对比此前28日，WeightProgress按周一自然周求均，MovementWeekReview列整周安排。综合周报是新的只读投影，不能更改这些既有窗口或冒充新评分。

遵守specs/001、003、004、005：固定分析时区、未知不补0、kg、同日末次体重、均值至少3个有效日门槛、只读健康、演示隔离、iCloud默认关闭。用户要求暂缓真机，本阶段及后续Build均不操作实体设备。

## Decisions

### 1. 回顾已结束日，等长星期对比

**方案**：详情提供“本周”“上周”，默认本周。设固定分析时区的今天00:00为D、所在周一00:00为M。

| 选择 | 当前区间（半开） | 对比区间（半开） |
| --- | --- | --- |
| 本周 | [M,D)，即周一至昨天 | [M−7日,D−7日)，相同星期范围 |
| 上周 | [M−7日,M)，完整周一至周日 | [M−14日,M−7日)，此前完整周 |

三类数据共用区间，排除今天未结束日及未来安排。日数n由Calendar逐日推进，不以86400秒相除；显示日期、分析时区、n个已结束日和“本周截至昨天”。周一默认n=0，显示“本周尚无已结束日，可查看上周”，不自动切换或套用上周数值。部分周期不称完整周。

**为什么**：避免今天未完成的计划被当失败、以及今天半天和上周全天比较。新周报不修改旧近7日/28日回顾和体重卡片。

**备选**：含今天并按上周全天比存在边界差异；默认最近完整周易被误认为本周，故只作可选项。此决策需Gate 2确认。

### 2. 三类事实独立汇总，无总分

**睡眠**：只消费一致profile的HealthReport.history.sleepMinutes。按原报告分析日归属，含主睡眠与小睡，不重新拆分。有限且≥0为有效，真实0保留、nil未知。日期在区间内、已结束且在report.asOf已达到原14:00结算时点才计入；不以墙钟伪装已重读。各段至少3个有效日才给各自均值，两者都有才给差值；显示N/n、分钟及含小睡。无需准备度基线即可看睡眠，不新增平均准备度、睡眠分、债务或规律性算法。

**体重**：取at≤now且recordedAt≤now的合法记录，按分析日选最后采样，at同值依次用recordedAt、id定序，与WeightProgress一致。取选中区间、每日等权，各段≥3不同有效日才求均，显示N/n、kg。均值按0.1kg显示后相减；睡眠同样按显示整数分钟后相减。无均值不拿起始体重/单次记录替代，不称脂肪变化、不预测达标日期。旧体重卡保留自身窗口。

**运动执行**：逐日按PlanningState.scheduledEntry取已生效历史计划，自动周要求同分析时区且effectiveFrom已生效。旧手动模板无planHistory、生效时间未知时不反推历史，仅用已保存当日entry并说明历史可能不全。无安排不等于休息。

每个有计划日采用互斥状态：选择休息优先；否则手动完成且健康证据达标为“两者均有”，仅手动为“手动确认”，仅可靠健康记录达标为“健康记录达标”，其余“待确认”。复用WorkoutCompletion和既有活动名映射；无记录、类型不支持、缺可靠活跃区间不称未运动或0分钟。健康读取截止取有效report.asOf，profile/来源/时区不符则停用自动判定，保留人工标记。

汇总列安排数、手动确认（含两者均有）、健康记录达标（含两者均有）、去重完成数、休息、待确认，明确两种证据存在交集。去重完成+休息+待确认=安排数。无安排不出0%或100%，首版不新增完成率/加量规则。休息日有运动证据也不进入完成数，详情可独立列证据；自动证据删除可回退，人工标记独立保留。始终说明计划完成不代表减脂达标。

**备选**：把人工完成换算运动分钟或把未知判失败都会误报，故排除。

### 3. 纯展示模型，不落盘、不扩权

**方案**：拟新增Core的IntegratedWeeklyReview.swift，含范围枚举、窗口、三类汇总和动作枚举。主线程一次捕获now、timeZoneID、profile、report?、planning、workoutRecords与演示标记；模型不持有HealthKit或调用仓库，SwiftUI只消费模型。

报告需source与演示标记一致、timeZoneID与分析时区一致、configurationVersion与profile.version一致、asOf≤now；否则睡眠/自动判定标“报告不可用于当前设置”。旧的一致报告可列截至asOf已结算事实，显示健康读取时间和不足；不套用指标15分钟有效期否定历史均值。无健康报告仍可生成体重/人工计划部分。

不新增Codable缓存、RepositoryState字段、通知、后台任务、健康类型、Watch协议、组件、云同步或依赖。投影随输入重算，清除或修订不保留旧周报。integrated-weekly-review-v1只是展示规则版本，不改评分版本。

### 4. 紧凑入口与二级详情

**方案**：拟新增Apps/iOS/IntegratedWeeklyReviewViews.swift。今天现有主体下方一张紧凑卡：标题/窗口、三行摘要、查看周报。趋势各主题共用一个“综合周报”二级入口，不加主题或底部Tab；两入口打开同一详情。详情范围只在本次打开期间保留，不写iCloud偏好，不影响旧7/30日筛选或滚动位置。

详情顺序：周期/更新时间→睡眠→运动执行→体重→下一步。前三块可展开逐日证据，未知显示未记录/待确认，不以0画满图，不新增曲线或总分。动态字体垂直布局、不固定文字高；系统导航栏不覆盖内容。VoiceOver可读窗口/有效数/值或原因/时间，颜色非唯一状态。

演示切换、清除及dataIdentity变化关闭旧详情；跨分析日前台恢复更新窗口，演示固定demo.asOf。进入其他Tab后保留原趋势筛选；周报不直接编辑历史执行状态。

### 5. 下一步仅为操作入口

固定顺序最多3项，不根据体重差值或分数生成运动增量：

1. 报告缺失、不符或asOf未覆盖当前区间终点：查看健康连接（我的）。
2. 当前体重有效日<3且n>0：记录体重（既有表单），解释门槛，不要求补填过去未知体重。
3. 有计划待确认：查看计划与记录（活动），不自动勾选。
4. 当前睡眠有效日<3且n>0：查看睡眠记录，不推断拒绝授权。
5. 以上均未命中：自主回顾下周安排（既有计划管理）；无计划则设置活动计划。

n=0仅提供查看上周和原功能入口，不要求补记录。动作只导航/打开既有表单；写入仍需原确认，下一周仍受完整周/反馈/预览采纳规则约束，不承诺点一次即生成有效下周安排。

## Architecture

```text
DashboardModel当前同源输入（只读捕获）
 → AnalysisClock窗口与来源/profile校验
 → IntegratedWeeklyReview纯聚合
 → 今天摘要 / 趋势入口 → 同一周报详情
 → 用户点击 → 原睡眠/活动/体重/设置界面 → 原确认流程
```

拟改：Core新模型与Tests；iOS新视图与PhoneDashboardView入口，必要时DashboardModel只读组装；根规格001及README说明在Gate 2确认后、实现前更新。存储、评分、HealthKitReader、Watch与iCloud代码不改。上述新增路径为计划产出，尚未创建业务文件。

## Risks / Trade-offs

| 风险 | 缓解措施 |
| --- | --- |
| 和旧近7日/28日回顾、含今天体重卡不同窗 | 每处列完整日期，不用新均值替换旧卡 |
| 周一/前两日无法求均 | 明确截至昨天/0日/至少3有效日，可选上周，不回退数字 |
| 已结束日历史尚未结算 | 按report.asOf检查原14点门槛，不假装新读取 |
| 旧计划缺生效时间/自动周时区不同 | 只用可靠历史/显式entry并标限制，不反推 |
| 人工/自动重复计数、休息被抹除 | 互斥状态、计数恒等式、休息优先 |
| 删除记录使完成度回退 | 纯投影重算，显示读取时间与修订说明 |
| 清除/演示/午夜展示旧来源 | dataIdentity失效、前台重算、演示时钟固定 |
| 字体与滑动复发 | 不固定文字高、不用覆盖顶栏，长文和辅助字号单独验证 |
